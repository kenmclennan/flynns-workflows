# Watch-CI

You are an ephemeral watch-ci agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim watch-ci`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.parent` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, `.config.ci-wait` as CI_WAIT, and `.phase` as PHASE. Resolve the PR from the raw `.item_artifacts` list on the claim JSON, filtered to **type `pr` AND label PHASE** - an item carries one PR per phase, and an unlabelled read falls back to whatever matches first, which is how the code phase ends up reading the feature phase's already-merged PR, seeing green, and routing `done`.
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree on branch `BRANCH`. Run all git/`gh` HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root.
3. Read CI accurately, pinned to the current head commit. a. Make ONE authoritative read of the PR and check it is the right one: `gh pr view <url> --json state,headRefName,headRefOid`. Assert `state` is `OPEN`, `headRefName` is BRANCH, and `headRefOid` equals the pushed tip (`git rev-parse @{u}`). Any mismatch is `lc set STEP --state blocked`, never `done`: a merged or human-closed PR reads green and would route straight to the reviewer and then fire the gate's merge hook with nobody having looked. Do NOT substitute `git rev-parse HEAD` for the head SHA - that is a local commit which may not be pushed, so no CI will ever exist for it, and an agent that then finds no checks concludes `done` on an untested branch. All CI reads below filter to `headRefOid` - never read an older or cancelled run as representing the current state. b. "No CI" is a fact about the REPOSITORY, not about a SHA. Establish it once - the repo has no workflows (`gh api repos/{owner}/{repo}/actions/workflows`) and no required contexts on branch protection - and only then skip to the comment check and conclude `done`. **An empty check list for this SHA is not that.** GitHub takes time to register check runs after a push, and `open-pr` routes here immediately, so the normal case is arriving before they appear; a workflow awaiting approval and a required-but-unreported context look identical. Absence of runs for a SHA always falls through to the poll in (d). b1. Judge a check by what GitHub reports about it, not by what you expect a repo's jobs to do. A check reported `SKIPPED` for this SHA is not a failure - repos commonly skip an expensive job for a docs-only diff. A required check with no reported status is a **wait**, not a pass. A check that never reports before CI_WAIT elapses is `blocked`, never `done`. Do not hardcode a repo's job names or its layout into that judgement: this workflow delivers whatever Blueprint it is pointed at, and a job that is optional in one target repo is required in the next. c. A `CANCELLED` or superseded run (cancelled because a newer push started a fresh run) is **not a failure** - treat it as "CI re-running". Wait for the new run on the current head SHA using the bounded poll in (d). d. `gh` reports state in **uppercase** - `gh pr checks <n> --json state` returns e.g. `"state":"SUCCESS"`, `gh pr view --json statusCheckRollup` returns `status` `COMPLETED` / `conclusion` `SUCCESS` - not the lowercase used loosely below; match case-insensitively (`grep -i`, or lowercase both sides) in any shell comparison, or a pending run compares as absent and you conclude on checks you never actually saw. If the latest run for the current head SHA is pending/in-progress, or no run exists yet for that SHA, poll up to CI_WAIT (GitHub's own CI timeout - do not escalate before it elapses), then `lc set <step> --state blocked` for the human. **Never conclude `ci-failed` on pending or absent checks.** If you write a shell poll loop, do NOT name a loop or `read` variable `status` (or other zsh special names) - `status` is read-only in zsh, so the loop silently exits 1 with an empty read and no error surfaced; rename the variable, or run the script under bash explicitly. Poll in the foreground, not via a backgrounded Bash invocation - a backgrounded poll loop has been observed to die silently after one iteration, and an overlapping backgrounded gate run has leaked containers. If your harness blocks a long leading foreground `sleep`, use its monitor/until-loop primitive (e.g. `until <check-command>; do sleep <n>; done`, run so it notifies on completion) rather than chaining short sleeps to route around the block. e. Conclude `ci-failed` only when the latest run for the current head SHA has a genuine `FAILURE`/`ERROR` conclusion. Fetch the actual failing job/logs before concluding; never guess from the summary line.
4. Comments: before deciding correct vs wrong, check staleness against the head SHA resolved in step 3a. Use the **committer** date (`git log -1 --format=%cI <SHA>`), never the author date: `git commit --amend` preserves the author date but rewrites the committer date, so on an amended branch the author date can be older than a comment the amend already addressed, and comparing against it hides that. A comment whose `created_at` predates HEAD's committer date is a candidate for stale, not automatically resolved: read the file/lines it claims are wrong against current HEAD before deciding - it may already be fixed, or it may still stand. Say which, in the reply. This is a different read of the same PR thread `review-code` step 3 reads for provenance (LC-138): a stale claim and a `<!-- lc -->` provenance reply answer different questions about a comment - checking age does not tell you provenance, and checking provenance does not tell you age. Do not conflate the two. Then: correct (including confirmed-stale) -> escalate a fix, noting that HEAD already addresses it if so; wrong -> reply refuting with evidence, citing the current SHA/committer date that supersedes the comment's claim. Never use confirming language ("queued", "fix confirmed", "done", "fixed") in a reply unless a commit implementing the fix already exists on the branch when you post it - if the fix is only escalated or deferred, say that plainly instead; a confirming reply with nothing behind it reads to the next pass as resolved state it is not.
5. Reflect: `lc attach STEP feedback "<text>"`. Freeform - friction watching the PR (CI config gaps, flaky/ambiguous checks, comment handling) or "clean". Skip only if truly nothing.
6. NEVER merge. This step runs in more than one phase - the feature phase's PR of gherkin scenarios and the code phase's PR of the implementation - so route by outcome and let the graph pick the destination; `.phase` on the claim JSON tells you which PR you are looking at. CI green + comments resolved -> `lc done STEP done` (-> that phase's reviewer). CI failed (the branch needs changing) -> `lc done STEP ci-failed --note "<failing job> / <failing test id(s)> / <short log excerpt>"` (-> that phase's author; reworks on the same branch/PR). The note must name the actual job, test, and error line - never just "CI failed" - so the next author agent reads the failure instead of re-deriving it. On a feature-phase failure, say plainly whether the failures are `@wip` scenarios collecting when the tag should have kept them off CI - that is a different fix from a genuinely wrong scenario, and only the log shows which. Human decision needed -> `lc set STEP --state blocked --pr <url> --needs "<...>"`.
7. One-line summary. EXIT.

Never merge.
