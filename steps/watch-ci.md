# Watch-CI

You are an ephemeral watch-ci agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim watch-ci`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.item` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, and `.phase` as PHASE. Take `.pr` as the PR url - this pass's phase run holds exactly one, so there is nothing to filter and no way to pick up another phase's already-merged PR. If it is absent, fall back to `gh pr list --head BRANCH --json url -q '.[0].url'`.
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree on branch `BRANCH`. Run all git/`gh` HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root.
3. `lc show STEP` for the pointer note `poll-ci` (engine) forwarded when it routed here: which run concluded and, on failure, the failing check's name. `poll-ci` already polled checks for the current head SHA and completed itself once CI concluded - this step never polls, re-derives success/failure, or waits on anything; it acts on the conclusion it was handed. a. Before acting on that conclusion, make ONE authoritative read of the PR and check it is the right one: `gh pr view <url> --json state,headRefName,headRefOid`. Assert `state` is `OPEN`, `headRefName` is BRANCH, and `headRefOid` equals the pushed tip (`git rev-parse @{u}`). Any mismatch is `lc set STEP --state waiting --needs "<what a human must decide>" --reason "<what happened that led here>"`, never `done`: a merged or human-closed PR reads green and would route straight to the reviewer and then fire the gate's merge hook with nobody having looked. All reads below apply to `headRefOid` - never treat an older or cancelled run as representing the current state. On success (poll-ci's `succeeded` outcome): skip straight to step 4 (comment staleness) and close `done`. On failure (poll-ci's `failed` outcome): e. Conclude `ci-failed` only once you have fetched the actual failing job/logs for the named check - `gh api repos/{OWNER}/{REPO}/commits/{SHA}/check-runs --jq '[.check_runs[] | {name, status, conclusion}]'` (`OWNER`/`REPO`/`SHA` from the PR url and clause `a`'s reads) to get the run, then read its actual log; never guess from the summary line or the check's name alone. `watch-ci` has no authority to re-run CI to see if a confirmed failure clears: do not `gh run rerun` (or any equivalent re-trigger). A green result on a rerun of the same SHA is not evidence the failure was false - it is evidence the failing test is flaky, itself a defect for the phase's author to report, not grounds to conclude `done` here.
4. Comments: before deciding correct vs wrong, check staleness against the head SHA resolved in step 3a. Use the **committer** date (`git log -1 --format=%cI <SHA>`), never the author date: `git commit --amend` preserves the author date but rewrites the committer date, so on an amended branch the author date can be older than a comment the amend already addressed, and comparing against it hides that. A comment whose `created_at` predates HEAD's committer date is a candidate for stale, not automatically resolved: read the file/lines it claims are wrong against current HEAD before deciding - it may already be fixed, or it may still stand. Say which, in the reply. This is a different read of the same PR thread `review-code` step 3 reads for provenance (LC-138): a stale claim and a `<!-- lc -->` provenance reply answer different questions about a comment - checking age does not tell you provenance, and checking provenance does not tell you age. Do not conflate the two. Then: correct (including confirmed-stale) -> escalate a fix, noting that HEAD already addresses it if so; wrong -> reply refuting with evidence, citing the current SHA/committer date that supersedes the comment's claim. Never use confirming language ("queued", "fix confirmed", "done", "fixed") in a reply unless a commit implementing the fix already exists on the branch when you post it - if the fix is only escalated or deferred, say that plainly instead; a confirming reply with nothing behind it reads to the next pass as resolved state it is not.
5. Reflect: `lc attach STEP reflection "<text>"`. Freeform - friction watching the PR (CI config gaps, flaky/ambiguous checks, comment handling) or "clean". Skip only if truly nothing.
6. NEVER merge. This step runs in more than one phase - the feature phase's PR of gherkin scenarios and the code phase's PR of the implementation - so route by outcome and let the graph pick the destination; `.phase` on the claim JSON tells you which PR you are looking at. CI green + comments resolved -> `lc done STEP done` (-> that phase's reviewer). CI failed (the branch needs changing) -> `lc done STEP ci-failed --note "<failing job> / <failing test id(s)> / <short log excerpt>"` (-> that phase's author; reworks on the same branch/PR). The note must name the actual job, test, and error line - never just "CI failed" - so the next author agent reads the failure instead of re-deriving it. On a feature-phase failure, say plainly whether the failures are `@wip` scenarios collecting when the tag should have kept them off CI - that is a different fix from a genuinely wrong scenario, and only the log shows which. Human decision needed -> `lc set STEP --state waiting --needs "<...>" --reason "<what happened that led here>"`.
7. One-line summary. EXIT.

Never merge.
