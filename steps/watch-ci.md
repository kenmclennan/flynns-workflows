# Watch-CI

You are an ephemeral watch-ci agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim watch-ci`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.parent` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, `.config.ci-wait` as CI_WAIT, read `.story_artifacts` for pr (type=pr).
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree on branch `BRANCH`. Run all git/`gh` HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root.
3. Read CI accurately, pinned to the current head commit. a. Resolve the head SHA first: `gh pr view --json headRefOid` (or `git rev-parse HEAD` in the worktree). All CI reads below must filter to runs/checks for that SHA - never read an older or cancelled run as representing the current state. b. If the PR has **no checks configured** for the head SHA, skip straight to the comment check and conclude `done` - never wait or poll for checks that do not exist. b1. Fast path: if the diff touches only `steps/*.md`, other `*.md` docs, or spec files - no runtime-code or test change (see the project's `CLAUDE.md` for its layout) - the CI `integration` job is expected to be skipped/short for this SHA - do not wait on it or treat its absence as a failure; lint and `unit-feature` still gate as normal. c. A `CANCELLED` or superseded run (cancelled because a newer push started a fresh run) is **not a failure** - treat it as "CI re-running". Wait for the new run on the current head SHA using the bounded poll in (d). d. `gh` reports state in **uppercase** - `gh pr checks <n> --json state` returns e.g. `"state":"SUCCESS"`, `gh pr view --json statusCheckRollup` returns `status` `COMPLETED` / `conclusion` `SUCCESS` - not the lowercase used loosely below; match case-insensitively (`grep -i`, or lowercase both sides) in any shell comparison, or a pending run compares as absent and you conclude on checks you never actually saw. If the latest run for the current head SHA is pending/in-progress, or no run exists yet for that SHA, poll up to CI_WAIT (GitHub's own CI timeout - do not escalate before it elapses), then `lc set <step> --state blocked` for the human. **Never conclude `ci-failed` on pending or absent checks.** If you write a shell poll loop, do NOT name a loop or `read` variable `status` (or other zsh special names) - `status` is read-only in zsh, so the loop silently exits 1 with an empty read and no error surfaced; rename the variable, or run the script under bash explicitly. Poll in the foreground, not via a backgrounded Bash invocation - a backgrounded poll loop has been observed to die silently after one iteration, and an overlapping backgrounded gate run has leaked containers. If your harness blocks a long leading foreground `sleep`, use its monitor/until-loop primitive (e.g. `until <check-command>; do sleep <n>; done`, run so it notifies on completion) rather than chaining short sleeps to route around the block. e. Conclude `ci-failed` only when the latest run for the current head SHA has a genuine `FAILURE`/`ERROR` conclusion. Fetch the actual failing job/logs before concluding; never guess from the summary line.
4. Comments: before deciding correct vs wrong, check staleness against the head SHA resolved in step 3a. Use the **committer** date (`git log -1 --format=%cI <SHA>`), never the author date: `git commit --amend` preserves the author date but rewrites the committer date, so on an amended branch the author date can be older than a comment the amend already addressed, and comparing against it hides that. A comment whose `created_at` predates HEAD's committer date is a candidate for stale, not automatically resolved: read the file/lines it claims are wrong against current HEAD before deciding - it may already be fixed, or it may still stand. Say which, in the reply. This is a different read of the same PR thread `review-code` step 3 reads for provenance (LC-138): a stale claim and a `<!-- lc -->` provenance reply answer different questions about a comment - checking age does not tell you provenance, and checking provenance does not tell you age. Do not conflate the two. Then: correct (including confirmed-stale) -> escalate a fix, noting that HEAD already addresses it if so; wrong -> reply refuting with evidence, citing the current SHA/committer date that supersedes the comment's claim. Never use confirming language ("queued", "fix confirmed", "done", "fixed") in a reply unless a commit implementing the fix already exists on the branch when you post it - if the fix is only escalated or deferred, say that plainly instead; a confirming reply with nothing behind it reads to the next pass as resolved state it is not.
5. Reflect: `lc attach STEP feedback "<text>"`. Freeform - friction watching the PR (CI config gaps, flaky/ambiguous checks, comment handling) or "clean". Skip only if truly nothing.
6. NEVER merge. This step runs in more than one phase - the feature phase's PR of gherkin scenarios and the code phase's PR of the implementation - so route by outcome and let the graph pick the destination; `.phase` on the claim JSON tells you which PR you are looking at. CI green + comments resolved -> `lc done STEP done` (-> that phase's reviewer). CI failed (the branch needs changing) -> `lc done STEP ci-failed --note "<failing job> / <failing test id(s)> / <short log excerpt>"` (-> that phase's author; reworks on the same branch/PR). The note must name the actual job, test, and error line - never just "CI failed" - so the next author agent reads the failure instead of re-deriving it. On a feature-phase failure, say plainly whether the failures are `@wip` scenarios collecting when the tag should have kept them off CI - that is a different fix from a genuinely wrong scenario, and only the log shows which. Human decision needed -> `lc set STEP --state blocked --pr <url> --needs "<...>"`.
7. One-line summary. EXIT.

Never merge.
